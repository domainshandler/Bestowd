# MAUI Mobile App (v1) Implementation Plan

**Goal:** The primary Bestowd client, for iOS and Android, built with .NET MAUI on the same API as the web app. It has the mockup's four tabs (Home, People, Gifts, Ideas), the family and person screens, logging gifts, invite links, and **push reminders**.

**Reference:**
- `docs/superpowers/specs/2026-11-18-data-model-realignment.md`
- `docs/superpowers/plans/2026-11-20-web-screens.md`: the same screens, data and look.
- Navigation Tabs Mockup: it was designed at phone size, 390×844.

**Stack:**
- .NET 10 (LTS) and .NET MAUI.
- CommunityToolkit.Mvvm and CommunityToolkit.Maui.
- `System.Net.Http.Json` for the API client.
- xUnit for the tests.
- Firebase Cloud Messaging (FCM) for push, on Android and on iOS through APNs.

## Build environment (needed before any task)

- **.NET 10 SDK.**
- **Workloads:** `dotnet workload install maui-android` on Linux, Windows or macOS. `maui-ios` needs macOS with Xcode.
- **Android:** the SDK and a JDK. `dotnet build -t:InstallAndroidDependencies` fetches them.
- **iOS:** a Mac with Xcode and an Apple developer account. You need one for device builds, push, and Sign in with Apple.
- **CI:** GitHub Actions. Android and `Bestowd.Core.Tests` run on `ubuntu-latest`; iOS runs on `macos-latest`.

Everything that can be tested lives in `Bestowd.Core`. The MAUI project only holds the XAML and the platform glue.

## API changes the app needs (in this repo, with tests)

1. **Several Google client IDs.**
   - Each mobile app gets its own Google client ID, and `verifyGoogleToken` currently accepts only `GOOGLE_CLIENT_ID`.
   - Add `GOOGLE_CLIENT_IDS`, a comma-separated list that the token audience is checked against.
2. **Devices.**
   - A `Device` model: `id`, `userId`, `platform` (ANDROID or IOS), `token` (unique), `createdAt`, `lastSeenAt`.
   - `POST /me/devices { platform, token }` upserts a device. `DELETE /me/devices/:token` removes it on sign-out.
3. **Push delivery.**
   - `services/push.ts` sends through the FCM HTTP v1 API, using a service-account JSON in the env variable `FCM_SERVICE_ACCOUNT`.
   - `runReminderScan` sends one notification per due reminder to each of the user's devices, for example: "Maya's birthday is in 3 days — needs a gift".
   - Tokens FCM reports as invalid are deleted.
   - Tests mock the FCM call.
4. **More reminder types**, all from the scope:
   - a *buy reminder*: the occasion is within 7 days and its status is still NOT_STARTED;
   - a *card reminder*: `needsCard` is true and `cardDone` is false, 3 days out;
   - a *thank-you reminder*: on `thankYouDueAt` for received gifts not yet thanked.

   Each is a pure function that is unit-tested.
5. **App links:**
   - `/.well-known/assetlinks.json` (Android) and `/.well-known/apple-app-site-association` (iOS), served by the web host.
   - The web `/join/:token` page stays as the fallback.

## Tasks

1. **Scaffold.**
   - Create the solution, the three projects, and `Directory.Build.props` (nullable on, warnings as errors).
   - Make `dotnet test` and `dotnet build -f net10.0-android` pass.
   - Add a GitHub Actions workflow.
2. **Core models and API client.**
   - Records with `System.Text.Json` source generation.
   - `BestowdApi` reads `{ error }` bodies into `ApiException` and attaches the bearer token from `ITokenStore`.
   - Tests use a fake handler covering success, 401, 404 and 410, the query strings, and bodyless POSTs.
3. **Auth.**
   - Google sign-in with the native SDKs, via a small binding or `WebAuthenticator` with PKCE. Either way the app sends the ID token to `POST /auth/google`.
   - The token is stored in `SecureStorage`, and a 401 sends the user back to sign-in.
   - Includes API change 1.
   - Sign in with Apple and email sign-in come with roadmap step 6. The App Store requires Apple sign-in before an iOS release, so that step must land before iOS submission.
4. **GroupState and shell.**
   - The TabBar with four tabs.
   - The account avatar sits in the top-right of each tab's title bar.
   - The group switcher appears only for users in several groups, with the same rules as the web app. It is tested in Core.
5. **Home:** the summary card, type chips, occasion rows, pull to refresh, and the Log a gift sheet.
6. **People and Family profile:** the same sections as the web plan. The invite button uses the native share sheet (`Share.RequestAsync`) with the invite URL.
7. **Person:** notes, occasions, Given/Received history by year, ideas, and the forms.
8. **Gifts:** year picker, totals, filters, grouping by occasion and year, Show value, and thank-you.
9. **Ideas:** person picker, repeat notice, top pick, Mark as bought, dismiss, and add.
10. **Forms as bottom sheets** (CommunityToolkit.Maui popups): family, person, occasion, gift and idea. The validation matches the API's rules.
11. **Join by link:**
    - App Links on Android and Universal Links on iOS open `join/{token}`.
    - The page shows the preview, signs the user in if needed, and then accepts the invite.
    - Includes API change 5.
12. **Push:**
    - Ask for notification permission after the first occasion is added, not at launch.
    - Register the FCM token with `POST /me/devices`, and remove it on sign-out.
    - Tapping a notification opens the occasion's person or family.
    - Includes API changes 2–4.
13. **Polish:**
    - Empty, loading and error states.
    - Accessibility: semantic descriptions on icon buttons, 44pt touch targets, and Dynamic Type.
    - Dark mode is out of scope for v1.

## Tests

- **`Bestowd.Core.Tests`:**
  - the API client;
  - GroupState: defaulting, remembering a choice, falling back;
  - formatting: UTC dates, "In N days", money;
  - view-model logic: home summary counts, grouping gifts by occasion and year, the idea top pick and repeat notice, and the fields sent when joining.
- **API:** Vitest for devices, push (FCM mocked), the new reminder types, and multiple Google client IDs.
- **Manual on devices:** sign in, add a family and person, log a gift, an invite link opening the app, and receiving a push.

## Out of scope for v1

- Photo upload.
- Address-book import.
- Offline mode.
- Widgets.
- A tablet-specific layout.
